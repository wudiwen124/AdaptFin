# AdaptFin 设计说明

## 背景和目标

通用聊天模型可以解释投资概念，但直接用它分析具体股票时会遇到三个问题：数据可能过期，计算过程不可验证，不同对话之间也记不住用户的风险承受能力。AdaptFin 的目标是把这些问题放进一个可检查的流程中。

项目面向 A 股，核心使用场景是：

1. 用户完成风险问卷，系统保存风险等级、投资期限和仓位约束。
2. 用户查询个股、ETF 或持仓，系统调用数据工具取得行情、财务、估值和公告。
3. 系统结合用户画像生成研究参考，并保留数据来源。
4. 后续对话可以通过用户 ID 恢复持仓、偏好和会话上下文。

项目定位为研究辅助工具。它不接券商账户，不自动下单，也不把模型输出包装成收益承诺。

## 第一版范围

第一版保留以下功能：

- A 股个股、ETF 和主要指数的行情查询。
- 日 K、均线、RSI、波动率和最大回撤。
- 财务摘要、估值、公司概况和个股公告。
- 单标的研究和持仓研究。
- 风险测评、重新测评和风险约束。
- 用户画像、持仓、偏好和风险历史。
- 网页聊天、API、命令行和 Docker 启动方式。

暂不包含：

- 实盘交易、自动下单和资金账户绑定。
- 分钟级或逐笔行情。
- 自建因子库、回测平台和收益预测。
- 完整的美股、港股和全球宏观数据。

这些边界主要是为了控制数据授权、合规风险和维护成本，不是因为架构不能扩展。

## 为什么使用多个执行角色

项目把不同职责拆开，主要目的是限制每个节点能看到什么、能做什么。

### Supervisor

负责识别当前请求属于行情、研究、风险测评、持仓还是普通对话。常见请求先通过关键词和句式规则判断，规则无法判断时再调用成本较低的模型。Supervisor 还会完成股票名称解析、指代消解、用户画像加载和每轮状态清理。

### Market

只调用行情工具，返回现有数据。它不负责解释涨跌，也不输出买卖意见。这样可以把数据获取和内容生成分开，接口异常时也容易判断问题出在哪一层。

### Research

对每只股票创建独立研究任务，任务内部并行运行三个方向：

- 基本面：公司概况、财务摘要和估值。
- 技术面：K 线、均线、RSI、波动和回撤。
- 资讯面：公告和相关资讯。

合并结果时保留证据列表和数据日期。持仓研究同样使用这一流程，只是会同时处理多只股票。

### Risk

风险问卷固定在 UI 和后端中使用，不依赖模型猜用户选择。评分与风险等级由规则计算。用户可以重新测评，新结果完成前旧画像仍然有效；填写过程中也可以取消。

### Advisor

接收研究结果、风险画像、持仓、偏好和最近对话，生成面向用户的回答。系统提示词要求区分事实、计算和推测，普通闲聊则使用另一套提示，不套金融分析模板。

### Auditor 与 Memory Writer

这两个是规则/存储节点，不是额外的大模型 Agent。Auditor 检查免责声明、数字和日期来源、指令性表述和时点边界。发现问题时允许有限次数回修。Memory Writer 负责把风险画像、持仓、偏好和会话结果写入对应存储。

## 一次请求的处理流程

```text
用户消息
  -> 加载 checkpoint 与用户画像
  -> Supervisor 分类 / 名称解析 / 指代消解
  -> 按意图进入执行节点
       Market / Research / Risk / Portfolio / Chat
  -> Advisor 生成回答
  -> Auditor 审计，必要时回修
  -> Memory Writer 写入变更
  -> 返回消息
```

Supervisor 是路由节点，不承担最终回答。Research 和 Portfolio 都可能触发多标的研究，内部使用 LangGraph 的 `Send` 并行分发，完成后再汇总。

## 状态设计

主状态主要包含以下字段：

- `messages`：当前会话消息。
- `user_id` 与 `thread_id`：用户和会话标识。
- `intent`：当前请求类型。
- `risk_profile`：风险等级、分数、投资期限和约束。
- `holdings`：持仓列表。
- `research_results`、`market_results`：各分支的结构化结果。
- `evidence`：工具名、参数、返回值、数据日期和来源。
- `risk_questionnaire`：问卷进度、临时答案和是否等待用户输入。
- `entities`：最近提到的证券，用于指代消解。

每轮请求只增加当前输入和必要状态。历史消息由 checkpoint 恢复，避免重新传入完整初始状态导致问卷进度被重置。

## 数据获取

`DataSourceRouter` 统一处理不同来源。默认顺序可配置，`demo` 作为最后兜底：

- `demo`：确定性的离线数据，适合测试和展示。
- `akshare`：实时行情、K 线、估值、业绩报表和东方财富个股公告。
- `baostock`：历史日线、周线和月线。
- `tushare`：可选，需要 token 和相应权限。

路由层负责 TTL 缓存、重试和降级。数据对象带有 `source`、`as_of`、`degraded` 等字段，后续节点可以判断当前是否为降级数据。

Function Calling 工具由 Pydantic schema 描述参数和返回结构。工具失败时返回明确错误，不把异常堆栈直接传给模型。

## 风险模型

问卷共 10 题，选项映射为固定分值。总分映射到 C1-C5，并给出权益比例、单标的上限和投资期限约束。风险等级计算、持仓约束和提示文案都在 Python 中完成。

风险测评结果写入历史表，当前画像单独保存。这样可以保留每次测评记录，也便于回答“上次测是什么等级”。

## 记忆设计

项目使用两层记忆：

### 会话记忆

LangGraph `SqliteSaver` 保存消息、意图、问卷进度和节点状态，文件为 `data/checkpoints.db`。同一个用户和线程可以继续上一轮对话；不同用户不会共享线程。

### 长期画像

`ProfileStore` 使用 SQLite 保存：

- 用户风险画像与测评历史。
- 持仓。
- 偏好和事实记录。
- 审计记录。

这些数据都按 `user_id` 隔离。对话结束后，只有识别到持仓或偏好变化时才写长期画像，普通查询不会产生无意义的更新。

### 指代和召回

实体注册表记录当前会话最近提到的证券。“它现在多少钱”“那只怎么样”会先解析为具体代码，再进入行情或研究分支。

偏好召回先使用 `BAAI/bge-m3` 生成向量，通过余弦相似度寻找相关记忆；embedding 服务不可用时退回同义词和关键词匹配。召回结果只作为上下文，不能替代风险约束和证据。

## 审计规则

审计主要检查以下内容：

1. 金融类回答是否包含“不构成投资建议”等风险说明。
2. 回答中的小数、日期和财务指标能否在证据中找到。
3. 是否出现直接要求买入、卖出或保证收益的表述。
4. 公告日期、财务报告期和 K 线日期是否晚于研究截止日。
5. 没有足够证据时，是否明确说明缺少哪些数据。

审计不是对所有语义的判断。复杂推理仍可能出现错误，因此项目保留证据列表和审计记录，方便回查。

## 服务与网页

FastAPI 提供聊天、画像、审计和健康检查接口。`/v1/chat` 使用 SSE，前端可以逐步接收状态和回答。

Streamlit 页面用于本地演示，包含用户切换、风险测评、持仓、画像、聊天和本地数据管理。页面采用左右消息气泡，发送后显示思考状态，并在对话结束后刷新侧栏数据。

## 评测方法

项目使用 9 条固定用例比较三种架构：

- `single`：单 Agent 使用全部工具。
- `fixed`：无论请求类型都执行固定研究流程。
- `supervisor`：当前实现，先分类再进入对应节点。

指标包括请求完成、路由是否合理、是否带免责声明、内容是否包含必要证据，以及平均模型和工具调用次数。评测不把股票涨跌作为指标，因为短期市场结果不能代表系统工程质量。

真实模型当前的全量结果记录在 `results/benchmark_real_three_arch_full.md`。样本量较小，结论只适用于这组用例。

## 已知问题

- `demo` 数据与真实数据的字段覆盖并不完全一致。
- 公告源可能调整页面结构，适配器需要定期检查。
- 新闻能力仍不完整。
- 审计可以核对明确数字，不能替代人工复核复杂推断。
- 当前没有登录、权限和多租户隔离，不适合直接公开部署。
- SQLite 适合单机使用，多实例部署需要换用集中式存储。

## 后续方向

优先级较高的工作是补充更多真实数据回归用例、完善新闻源、增强财务字段校验，并为备份恢复和用户数据删除增加更完整的测试。模型或多 Agent 数量不会作为升级目标，只有在现有流程无法解决具体问题时才增加节点。
