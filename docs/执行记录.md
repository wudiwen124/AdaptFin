# AdaptFin 开发记录

这份记录按开发顺序整理，主要写当时做了什么、碰到哪些问题，以及为什么选择某种实现。它不是完整提交日志，细节以代码和 `git log` 为准。

## 项目起点

最初的想法是一个包含行情查询、研究分析和风险测评的投顾助手。真正动手前，我先把范围收窄到 A 股、研究辅助和本地演示，原因有三个：

1. 接入实盘交易会带来账户、合规和权限问题，不适合作为个人项目的第一版。
2. 没有风险画像的“个性化建议”只是换一种说法的话术，风险测评必须进入主流程。
3. 真实模型输出不稳定，如果所有逻辑都交给模型，测试很难做，所以行情计算、问卷评分和审计尽量使用确定性代码。

第一版方案只定义了基础角色和工具，没有过多角色。后续加入 Supervisor、Advisor、Auditor 和 Memory Writer，是因为请求路由、答案合成、输出检查和状态写入确实需要分开处理。

相关文档：`docs/多Agent智能投顾助手-项目方案.md`。竞品调研的结论单独写在 `docs/多Agent智能投顾助手-竞品调研与架构设计.md`。

## 搭建基础层

项目先完成了配置、领域模型和 SQLite 画像存储。`pyproject.toml` 将依赖拆成基础、数据、服务、UI 和测试几组；`configs/settings.yaml` 与 `.env` 负责运行参数。用户、持仓、行情、研究报告和风险画像都使用 Pydantic 模型，避免各层继续传递无结构的字典。

数据层通过统一的 `DataSourceRouter` 访问数据源。`demo` 数据源不联网，用于测试和离线演示；`akshare`、`baostock` 和 `tushare` 都是可选适配器，采用延迟导入，避免只装基础依赖时导入失败。真实接口经常出现限流、字段变化和网络超时，所以中间增加了 TTL 缓存、重试和降级。

技术指标没有交给模型计算。`tools/indicators.py` 使用 Python 实现 MA、RSI、年化波动和最大回撤；风险问卷也用固定分值计算 C1 到 C5。这样做既方便单测，也能避免模型在不同回答里给出不一致的算术结果。

## 编排第一版

LangGraph 主图最初按“路由 -> 执行 -> 回答 -> 审计 -> 记忆”搭建。Supervisor 先使用规则识别常见请求，规则无法判断时再调用便宜的 router 模型返回 JSON。Market 只负责取行情，Research 通过 `Send` 为每只股票并行创建研究任务，Risk 处理问卷和画像，Advisor 合成回答，Auditor 做规则检查。

真实模型联调时遇到几类问题：

- 新版 LangGraph 的 `Send` 参数与旧示例不同，按当前版本调整了调用方式。
- 每轮请求都重新传入完整的初始状态，导致问卷进度被清空。之后只传本轮输入，并依靠 checkpoint 保存会话状态。
- router 模型会把 JSON 模板或 Markdown 代码块一起返回。`llm/text.py` 增加了代码块清洗和容错 JSON 解析。
- 研究阶段耗时不固定，出现过 `httpx.ReadTimeout`。网关增加了超时和重试，同时为模型额度耗尽准备了备用模型链。
- GLM-4.7-Flash 曾返回 1305 额度错误。模型配置改为可覆盖，避免某个免费模型不可用时整个链路停止。
- 风险测评完成后原本无法重做。Risk 节点增加了“重新测评”和“取消测评”，新结果完成前仍沿用旧画像。

## 证据审计和服务接口

最早的 Auditor 只检查是否带免责声明，实际作用不大。后来将工具返回结果保存为 `EvidenceRecord`，Advisor 引用的数字需要能在工具结果中找到。Auditor 还会检查日期、指令性买卖表述和需要人工确认的内容。发现问题时允许有限次数回修，超过次数就结束，避免图和模型互相循环。

与此同时增加了 FastAPI 服务层。`/v1/chat` 使用 SSE 返回事件，画像和审计记录分别通过 `/v1/profile/{user_id}` 和 `/v1/audit` 查询。应用使用 `create_app` 工厂函数，测试时可以直接注入 fake gateway 和临时数据库。

这一阶段的问题主要是接口状态和错误边界。模型或工具报错不能直接把内部异常返回给前端，因此服务层统一转换为事件或可读错误；会话线程使用 `user_id` 和线程 ID 区分，避免不同用户共用一个 checkpoint。

## 用户记忆

第一版记忆只记录了风险等级，Advisor 实际上读不到。之后补充了长期画像读取：每次请求前加载用户的持仓、偏好和历史测评，再把最近对话与召回结果送入 Advisor。

持仓和偏好采用规则优先的抽取方式。常见表达如“我买了 100 股 510300”“偏好红利低波”可以直接解析；规则覆盖不到的表达再由 LLM 抽取，并丢弃低置信度结果。抽取结果不是每次都写库，只有检测到用户资料发生变化时才更新，避免普通查询也产生脏写。

会话记忆和画像存储分开：

- `SqliteSaver` 保存 LangGraph 消息和节点状态，用于连续对话。
- `ProfileStore` 保存用户画像、持仓、偏好事实和风险历史，用于跨会话读取。

后续加入了实体注册表。用户先问“贵州茅台怎么样”，再问“它现在多少钱”时，路由前会把“它”解析为最近提到的 `600519`。这比把全部历史消息直接拼进提示词更稳定，也减少了无关上下文。

语义召回最初只使用同义词和关键词。后来接入 SiliconFlow 的 `BAAI/bge-m3`，写入记忆时保存 1024 维向量，查询时优先计算余弦相似度；接口不可用时仍可回到关键词召回。

## 评测与返工

项目准备了 9 条固定用例，覆盖行情、研究、风险、记忆和普通对话。评测脚本实现三种架构：

- `single`：一个 Agent 直接调用全部工具。
- `fixed`：不管问题类型都执行固定研究流程。
- `supervisor`：当前项目使用的动态路由和审计流程。

第一次真实全量评测出现了“只差一个用例”的情况。检查逐用例产物后发现，评测脚本复用了数据库中的 checkpoint，前一个用例的状态影响了后一个用例。之后每次运行改用独立 `run_id`，并清理评测会话；没有改动业务逻辑再重跑，得到当前报告。

真实三架构的完整结果如下：

| 架构 | 完成 | 免责声明 | 内容有据 | 平均 LLM 调用 |
|---|---:|---:|---:|---:|
| single | 9/9 | 4/9 | 1/9 | 1.67 |
| fixed | 9/9 | 8/9 | 5/9 | 3.78 |
| supervisor | 9/9 | 9/9 | 9/9 | 3.00 |

这些指标只衡量当前用例里的路由、合规和证据使用。样本只有 9 条，不能据此推断投资收益或一般场景下的模型能力。

## 真实数据与时点校验

接入真实数据后，前后出现过两个公告源。巨潮 `cninfo` 的查询结果较旧，实际快照停留在 2023 年底，因此后来换成东方财富个股公告。财务摘要也改为东方财富业绩报表，并验证了贵州茅台的主要字段。

研究问题可能带有明确截止日期。如果只在下游过滤，工具已经取到截止日后的数据，证据仍可能被误用，所以 `as_of` 被加入行情和 K 线请求，在数据源头限制结束日期；Auditor 再检查公告发布日期和财务报告期，防止晚于研究截止日的内容进入回答。

## 网页和交互

Streamlit 页面最初只有默认聊天组件，风险问卷、持仓和用户管理混在一起。后来按实际操作重新组织：

- 侧栏负责用户切换、风险画像、持仓和本地数据管理。
- 主区域显示风险和对话。用户消息在右，助手消息在左。
- 发送问题后先显示消息和“正在思考”，避免长时间无反馈。
- 对用户隐藏 `get_*` 工具名，来源改为“行情数据源”“东方财富公告”等可读名称。
- 用户说“买了 100 股 510300”后自动刷新侧栏，不再要求额外点击应用。
- 删除用户和清空用户前提供确认；早期 JSON 导出入口已从页面移除。
- 固定问题“吴帝文是谁”由路由层直接识别为普通对话，回答为“吴帝文是 AdaptFin 的开发者”，避免被误判成财经人物研究。

普通对话与金融分析使用不同提示词。早期“你好”也会套用风险测评话术，原因是 Advisor 没有判断 `intent=chat`。修正后，普通对话不强制套研究模板，金融问题仍执行免责声明和审计。

## 交付与部署

`Dockerfile` 使用 `python:3.12-slim`，Compose 映射 `8001` 端口并把 `./data` 挂载为持久目录。Windows 本机安装 Docker Desktop 时，WSL 数据目录不能直接放在 `D:\` 根目录，最终选择 `D:\25328\DockerDesktopWSL`。Docker Hub 拉取超时则配置国内镜像，并在 Dockerfile 中使用可访问的 PyPI 镜像。

CI 使用 Python 3.11 和 3.12 执行编译检查和 pytest。应用启动命令保留工厂函数写法，否则 uvicorn 无法直接找到 `create_app`：

```bash
python -m uvicorn advisor.service.app:create_app --factory --port 8001
```
